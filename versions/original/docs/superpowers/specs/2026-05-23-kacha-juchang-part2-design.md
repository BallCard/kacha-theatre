## §0 Part 2 文风约定（重要 · 出自 ADR-005 偏离 2）

**Part 2 剧情维持古风一致**，与 Part 1 视觉语言（古代批阅氛围 / 御史房 / 朱红印章）统一。

新需求文档曾建议 Part 2 走"现代口语化 + 网络热梗密集"路线，**本项目明确否决**，理由：
1. 视觉统一：Part 1 卡片是古风，Part 2 剧情若突变现代口语会让玩家感觉是两个产品
2. 工程稳定：现有 `storyEngine.ts` 已用古风调教过的 prompt 不重写
3. 时间预算：风格再设计 + prompt 重做 = 2-4h，25h 内不值

**Part 2 文风准则**：
- 半文半白御史腔为主，可以塞「周报 / KPI / 开会 / 划水 / 加班」等现代办公词制造反差
- 不强行塞 emoji、不使用 yyds / 绝绝子 等流行语缩写
- 嘲讽但不刻薄，不羞辱当事人

## §1 Part 2 定位与衔接

### 一句话（Part 2）
Part 1 的卡片出完后，用户点「召见御史·演今日剧」进入 Part 2 5 节点互动剧情：**同一张照片里的"你"**被 AI 写成今日摸鱼主角，每个节点 3 选项（顺应天命 / 逆天而行 / 中立观望），宜忌规则真生效，每节点 AI 配一张动漫风分镜图，6 种结局之一收尾，最后导出一张连环画长图。

### Part 1 → Part 2 衔接（叙事 + 数据双承接）

- **同一张照片**：Part 2 不再二次上传，直接复用 Part 1 用户上传的那张原图（在每节点分镜配图、连环画开篇都会用到）
- **结构化种子**：Part 1 `/analyze` 的返回结构是 Part 2 的**唯一数据种子**——

```
Part 1 输出 (奏折 JSON + 原图)
  ├── 原图              → Part 2 分镜配图的人物参考（gpt-image-2 的 reference image）
  ├── pose_type         → 主角开场姿态
  ├── desk_objects      → AI 在 5 节点中复用为"具体道具"
  ├── moyu_score        → 决定剧情整体基调
  ├── sign_type         → 签型基调（上签 vs 下下签影响走向）
  ├── level_tier        → 御史奏折调性强度（天尊段直接开光晕剧情）
  ├── report.paragraph  → 抽 1-2 个意象植入开场
  ├── report.yi         → 节点选项中至少 1 个对应"宜"，选了 +80% 成功率
  └── report.ji         → 节点选项中至少 1 个对应"忌"，选了 -100% 必翻车
```

**前端在 Part 1 卡片页加一个底部 CTA**：「召见御史·演今日剧」，点击进入 Part 2。不影响 Part 1 任何既有交互。

> Part 2 **不支持**单独"上传任意卡片图 OCR 再生剧情"的入口（详见 ADR-005 偏离 4）。唯一入口是 Part 1 直接透传 JSON。

## §2 5 节点结构

固定 5 个时段节点，对应打工人的一天：

| # | 时段 | 场景定位 | AI 必须用到的种子 |
|---|---|---|---|
| 1 | **辰时**（早晨）| 主角刚到工位，开局介绍 | `pose_type` + `desk_objects` 至少 1 件 |
| 2 | **午前**（上午）| 突发事件（领导 / 群消息 / 任务） | 上一节点用户选择 + `report.yi/ji` 各至少 1 项进选项 |
| 3 | **未时**（午后）| 困倦高峰，摸鱼诱惑最大 | 累计宜忌命中次数 |
| 4 | **申时**（下午）| 危机降临 | 累计命中数 + 上一节点结果 |
| 5 | **酉时**（临下班）| 终局抉择 | 全程上下文 → 直接连结局 |

每节点 3 选项 → 共 3⁵ = 243 条路径，但**结局只 6 种**（见 §4），由结局判定规则归并。

## §3 选项生成规则

### 3.1 策略三选一

每节点的 3 个选项**必须分别对应**：

| 策略 | 调性 | 成功率基线 |
|---|---|---|
| 🟢 顺应天命 | 老老实实摸鱼 / 装睡 / 划水 | 看是否撞上"宜" |
| 🔴 逆天而行 | 突然认真 / 主动表现 / 自首 | 看是否撞上"忌" |
| 🟡 中立观望 | 模棱两可 / 等等看 / 跟同事商量 | 50% 中性 |

### 3.2 宜忌强约束

**每节点至少 1 个选项命中"宜"，至少 1 个选项命中"忌"**（剩下 1 个中性）。

- 选"宜"对应项 → `success_rate += 80%`，剧情结果**正面**（蒙混过关 / 老板赞赏 / 同事佩服）
- 选"忌"对应项 → `success_rate -= 100%`（即必败）→ 剧情结果**必翻车**（被点名 / 加班 / 失态）
- 中性 → 50/50 抛硬币，正反两种 paragraph 都由 LLM 现场出

### 3.3 段位基调微调

| level_tier | 整体基调修饰 |
|---|---|
| 打工新丁 / 划水学徒 | 倒霉为主，偶有翻盘 |
| 摸鱼修士 / 划水侍郎 | 好坏参半，选择决定 |
| 摸鱼大将军 | 顺风局，但有小陷阱 |
| **假寐天尊** | 诸事皆宜，即使选错也有"贵人相助" |

## §4 6 结局（前端规则判定，不依赖 LLM 决策）

### 4.1 判定输入

5 节点跑完后，前端收集：
- `yi_hits`：用户选中"宜对应项"的次数（0-5）
- `ji_hits`：用户选中"忌对应项"的次数（0-5）
- `level_tier`：Part 1 段位

### 4.2 判定规则表（顺序匹配，第一个命中即用）

| 优先级 | 结局 | 触发条件 |
|---|---|---|
| 1 | **天降祥瑞** | `level_tier == 假寐天尊` 且 `yi_hits >= 3` |
| 2 | **御史降罚** | `ji_hits >= 3` |
| 3 | **逆天改命** | `level_tier ∈ {打工新丁, 划水学徒}` 且 `yi_hits >= 4` |
| 4 | **贵人相助** | `level_tier ∈ {打工新丁, 划水学徒}` 且 `ji_hits >= 2` 但未触发降罚 |
| 5 | **天命应验** | `yi_hits >= 3` 且 `ji_hits <= 1`（普通好运收尾） |
| 6 | **哭笑不得** | 其余所有情况（兜底，宜忌交织） |

### 4.3 结局内容

最后调用一次 LLM 生成 `final_verdict`（御史房最终裁决书），传入：
- 完整 5 节点剧情 + 用户全选择
- 结局类型 + 段位
- 字数约束：120-180 字

返回字段：
```json
{
  "ending_type": "天降祥瑞",
  "verdict": "卿今日紫微入命...",
  "yi_summary": "今日宜：摸鱼、查文档、假装思考（命中 4 次）",
  "ji_summary": "今日忌：开会、被点名（命中 0 次）",
  "title_award": "祥瑞天尊"  // 额外授予一个结局称号
}
```

## §5 API 设计

### 5.1 新增 `POST /plot/next` — 单节点剧情生成

**请求**：

```json
{
  "session_id": "sha1-of-image-base64-truncated-16",  // Part 1 出奏折时前端生成的会话 ID
  "node": 1,                                           // 当前要生成的节点号 1-5
  "seed": {                                            // 完整 Part 1 输出，每次都传（无状态）
    "pose_type": "趴桌型",
    "desk_objects": ["半杯冷美式", "青轴键盘", "黑屏显示器"],
    "moyu_score": 87,
    "level_tier": "摸鱼大将军",
    "report": {
      "paragraph": "紫微星偏移3度，案上美式已凉……",
      "yi": ["摸鱼", "划水", "假装思考"],
      "ji": ["开会", "改PPT", "接电话"]
    }
  },
  "history": [                                         // 节点 1 时为空数组
    {
      "node": 1,
      "scene_title": "辰时·御史临朝",
      "user_choice": "A",
      "outcome": "success",                            // success | fail | neutral
      "outcome_brief": "你迅速切到文档界面，领导点头走了"
    }
    // ... node 2 时长度 1，node 5 时长度 4
  ]
}
```

**响应**（HTTP 200）：

```json
{
  "node": 2,
  "scene_title": "午前·群中点将",
  "narrative": "你刚切回短视频，企业微信突然弹出一条消息：「@所有人 下午 2 点临时复盘，请提前准备」。一抬头，看见对面工位的小李正盯着你坏笑……",
  "options": [
    {
      "id": "A",
      "text": "假装没看见消息，继续查文档",
      "strategy": "顺应天命",
      "yiji_match": "yi",       // "yi" | "ji" | "neutral"
      "yiji_keyword": "查文档"
    },
    {
      "id": "B",
      "text": "立刻群里回「收到」，开始改 PPT",
      "strategy": "逆天而行",
      "yiji_match": "ji",
      "yiji_keyword": "改PPT"
    },
    {
      "id": "C",
      "text": "走到小李工位旁先打听情况",
      "strategy": "中立观望",
      "yiji_match": "neutral",
      "yiji_keyword": null
    }
  ]
}
```

**字段约束**：
- `scene_title`：8-12 字，必带时辰前缀
- `narrative`：80-150 字
- `options[*].text`：12-20 字
- `options` 顺序固定为 A=顺应 / B=逆天 / C=中立
- `yiji_match`：`yi` 和 `ji` 至少各出现 1 次

**校验失败**：retry 1 次，再失败走 §6 兜底节点池。

### 5.2 新增 `POST /plot/ending` — 终章裁决

**请求**：

```json
{
  "session_id": "...",
  "seed": { /* 同上 */ },
  "history": [ /* 5 个节点的完整选择 */ ],
  "ending_type": "天降祥瑞",  // 前端按 §4.2 规则算好后传入
  "yi_hits": 4,
  "ji_hits": 0
}
```

**响应**：

```json
{
  "ending_type": "天降祥瑞",
  "verdict": "卿今日紫微入命，案上冷美式竟得同事新斟之热咖……",
  "yi_summary": "今日宜：摸鱼、划水、假装思考（命中 4 次）",
  "ji_summary": "今日忌：开会、改PPT、接电话（命中 0 次）",
  "title_award": "祥瑞天尊"
}
```

### 5.3 性能要求

| 接口 | P50 | P95 | 兜底 |
|---|---|---|---|
| `/plot/next` | 2s | 4s | 节点池预录 6 条样本 |
| `/plot/ending` | 3s | 5s | 6 个结局各预录 1 段 |

**预生成优化**：前端在节点 N 出来后**立刻并发请求节点 N+1 的 3 个分支**（按 A/B/C 三种假设的 `outcome`），用户选哪个就秒出哪个，体感等待 0s。

```
渲染节点 N 文字 (用户读 5s)
    │
    ├─ 后台并发 /plot/next?assumed_outcome=success
    ├─ 后台并发 /plot/next?assumed_outcome=fail
    └─ 后台并发 /plot/next?assumed_outcome=neutral
    │
用户选完 → 命中其中一个预生成结果 → 直接渲染
```

成本：每节点 LLM 调用从 1 次 → 3 次（5 节点 = 15 次 + 终章 1 次 = 16 次），但用纯文本 LLM（如 gpt-4.1-mini / doubao-lite）单次 < 0.5 分钱，**总成本 < 1 毛/局**。

## §6 Prompt 工程

### 6.1 System Prompt（古风剧情编剧）

```
你是「咔嚓剧场·Part 2」的剧情编剧——御史房派驻的"演义官"。
你不再只是给图片打分的御史，现在要把一张办公室照片演成 5 幕剧。

调性（与 Part 1 卡片视觉一致，详见 §0 文风约定）：
- 半文半白御史腔为主，可以塞「周报 / KPI / 开会 / 划水 / 加班」等现代办公词制造反差
- 嘲讽但不刻薄，不羞辱当事人
- 不评价相貌、身份，只描述行为与桌面物件
- 不识别真实身份，用「卿」「该员」「尔」等代称
- 不强行塞 emoji、不使用 yyds / 绝绝子 等流行语缩写

剧情规则（铁律）：
1. 严格 5 节点，时段为辰/午前/未/申/酉
2. 每节点 3 选项，必须分别为「顺应天命 / 逆天而行 / 中立观望」
3. 每节点必须至少 1 个选项命中今日「宜」，至少 1 个命中今日「忌」
4. 选项里的宜忌关键词必须从用户上传的奏折原文里挑，不要造新词
5. 复用奏折中的桌面物件（desk_objects）入戏，让用户认出"这就是我的照片"
6. 严格输出 JSON，不要 markdown 包裹
```

### 6.2 User Prompt 模板（每节点）

```
请生成节点 {node} 的剧情。

【主角档案】
姿态：{pose_type}
桌面：{desk_objects}
段位：{level_tier}（摸鱼指数 {moyu_score}）

【今日奏折】
{report.paragraph}
宜：{report.yi}
忌：{report.ji}

【前情提要】
{history 拼接：每条是 "节点 N 选择 X → 结果 outcome：brief"}

【节点定位】
当前是「{时段名}」，剧情核心是 {场景定位}。

【输出要求】
- scene_title：8-12 字，带时辰前缀
- narrative：80-150 字，至少出现 1 个 desk_objects 元素
- options：3 个，顺序 A=顺应天命 / B=逆天而行 / C=中立观望
- 每个 option 的 yiji_match 必须是 "yi"/"ji"/"neutral"，3 个里至少各 1 个 yi 和 ji
- yiji_keyword 必须来自上方"宜"或"忌"列表

直接输出 JSON。
```

### 6.3 结局 Prompt

```
卿已演完 5 幕。请以御史房最终裁决书的口吻，120-180 字总结。

【段位】{level_tier}
【宜命中】{yi_hits} 次，分别：{matched_yi_keywords}
【忌命中】{ji_hits} 次，分别：{matched_ji_keywords}
【判定结局】{ending_type}

【结局调性】
- 天降祥瑞：极致顺风局，紫微高照，处处贵人
- 御史降罚：触犯天条，被御史台当庭训斥，加班 / 周报扣分 / 被点名
- 逆天改命：天命虽低但反抗成功，称号晋升
- 贵人相助：天命低但有同事/老板神助攻保住局面
- 天命应验：按部就班好运到底
- 哭笑不得：宜忌交织，啼笑皆非的小翻车

输出 JSON：{ ending_type, verdict, yi_summary, ji_summary, title_award }

title_award 是给主角的额外封号，4-6 字，比 Part 1 的称号更有戏剧性。
```

### 6.4 节点兜底池

每节点准备 3 条预录 JSON（顺/逆/中三个 outcome 分支各 1 条，覆盖通用办公室场景），LLM 全挂时按段位匹配最接近的兜底返回。位置：`server/data/plot-fallback/node{1-5}_{success|fail|neutral}.json`。

## §7 前端实现要点

### 7.1 路由

```
/             首页（拍照入口，复用 Part 1）
/poster       Part 1 海报页 + 编辑层（复用）
              └─ 底部 CTA「召见御史·演今日剧」→ /play
/play         Part 2 剧情主舞台
/ending       Part 2 终章 + 连环画导出
```

### 7.2 状态机

```typescript
type PlotState = {
  seed: AnalyzeResult;              // Part 1 输出
  currentNode: 1 | 2 | 3 | 4 | 5;
  history: NodeRecord[];            // 已完成节点
  prefetch: Record<Outcome, NodeData | null>;  // N+1 的 3 个预取结果
  yiHits: number;
  jiHits: number;
};

type NodeRecord = {
  node: number;
  scene_title: string;
  narrative: string;
  options: Option[];
  user_choice: 'A' | 'B' | 'C';
  outcome: 'success' | 'fail' | 'neutral';
  outcome_brief: string;
};
```

### 7.3 outcome 判定（前端纯本地，不调 LLM）

```typescript
function resolveOutcome(option: Option): Outcome {
  if (option.yiji_match === 'yi') return 'success';
  if (option.yiji_match === 'ji') return 'fail';
  return Math.random() < 0.5 ? 'success' : 'fail';  // 中立 50/50
}
```

剧情 narrative 中会针对 success/fail/neutral 各写一种走向，但 outcome 只决定**下一节点的 prefetch 选哪条**和**结局判定的 yi_hits/ji_hits 计数**。

## §6.5 分镜配图（每节点 1 张，gpt-image-2 链）

Part 2 的核心视觉爆点：**每个节点 AI 生成 1 张古风动漫分镜图**，主角面部特征延续 Part 1 上传照片里的人物。

**实现**：`src/frontend/src/services/storyEngine.ts` 已有 `generatePanelImage(panel, ctx)` 与 `generateEndingImage(spec, ctx)`，直接用：

- **基础模型**：`gpt-image-2`（`/v1/images/edits` 模式 + 参考图 = Part 1 上传的原图），失败降级 `gpt-image-1` → `dall-e-3`
- **风格 prompt**：古风 / 浮世绘 / 工笔晕染（与 Part 1 卡片视觉同源），不是日漫不是塞博
- **必须包含元素**：当前节点的时辰、场景、主角姿态、`desk_objects` 至少 1 件
- **必须排除**：现代品牌 logo、可辨识真实人物（避免 IP 风险）
- **尺寸**：默认 1024×1024（节省时间），高保真模式 1024×1536
- **质量**：默认 `low`（5-10s/张），主闭环跑通后可切 `medium`

**时间预算**：5 节点 × 8s ≈ 40s 图像生成，与节点间剧情阅读时间并发，体感等待可控。**降级路径**：图像生成失败时使用 `assets/demo/story_panel_default_*.png` 兜底。

### 7.4 连环画长图（终章导出，含每节点配图）

5 节点叙事 + 用户选择 + 终章裁决 → 拼成竖版长图：

```
┌─────────────────────────────┐
│   咔嚓剧场 · Part 2 全卷       │
├─────────────────────────────┤
│ 第一幕·辰时                 │
│ [Part 1 原图缩略]            │
│ {narrative}                 │
│ 卿选：A. {选项文字}          │
│ → 结果：{outcome_brief}      │
├─────────────────────────────┤
│ 第二幕·午前                 │
│ ...                         │
```
