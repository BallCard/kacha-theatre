## 做得好的地方 ✅

### 1. 文档驱动 + ADR 体系
**具体表现**：8 份 ADR 记录了每一个重大决策——赛道选择、技术栈、MVP 范围、Part 2 增量、品牌迁移、主线前端切换，每份含背景、选项对比、决策理由、后果分析。
**为什么好**：25 小时内有 6 次产品迭代、3 次前端主线切换、后端 T1-T13 阶梯推进，没有 ADR 体系的话，队友之间根本无法对齐。ADR-005 特别标注了"新协作者先读本 ADR 再读旧 ADR-001~004"。
**可复用经验**：黑客松中建立 "一个 PR 对应一个 ADR" 的轻量决策记录习惯，是防止方向漂移的最有效手段。

### 2. 后端分层设计（T1-T13 阶梯实现）
**具体表现**：后端代码按 13 个阶梯提交逐步搭建——T1 脚手架 → T2 等级映射 → T3 类型定义 → T4 schema 校验 → T5 兜底模板 → T6 Prompt 模块 → T7+T8 双 VLM 客户端 → T9 调度器 → T10 demo 匹配 → T11 埋点 → T12 接口暴露 → T13 prompt 验收。
**为什么好**：每层可独立测试（8 个 schema 测试、16 个 tier 测试、3 个 demo-match 测试、2 个 fallback 测试）；任一 VLM 挂掉自动走降级链；演示可走 demo 短路秒回。
**可复用经验**：先搭好校验+兜底+容错的"安全底座"再往上叠业务逻辑，这在 VLM 输出不确定性高的场景下是必选项。

### 3. 兜底策略的层层设防
**具体表现**：前端层面（`?mock=1`/`?offline=1` 走 sample JSON）、后端层面（VLM retry 2 次 → 换模型 → 兜底模板）、缓存层面（demo hash 匹配 + 持久化哈希缓存）、预热层面（`npm run warmup-story` 提前灌满 40 节点）。
**为什么好**：黑客松现场网络条件不可控，这四层兜底确保即使 VLM 全挂、服务器断网，demo 也能跑完。
**可复用经验**：对于依赖外部 AI API 的演示产品，兜底不是"备选"而是"主干"——demo 应默认走最稳的路径，实时 AI 调用作为"彩蛋"展示。

### 4. 缓存设计的前瞻性
**具体表现**：`server/lib/cache.ts` 实现了命名空间/哈希/版本号三级寻址，`CACHE_VERSION` 常量做缓存整体失效，`getOrSetJson` 原子写（tmp+rename），`getJson`/`putJson`/`getBinary`/`putBinary` 统一封装。
**为什么好**：Part 2 v2 的 40 节点全量缓存靠这套架构实现；演示时可预热；prompt 升级后 bump 版本号即整体废弃旧缓存。
**可复用经验**：一个完整的缓存层在 AI 应用中不是锦上添花——它决定了演示能否在 12ms 内秒回而非等 120s。

### 5. Part 2 性能优化组合拳
**具体表现**：
- **服务端推测预热**（`schedulePrefetch`）：节点 N 生成后 `setImmediate` fire-and-forget 触发 3 个子节点
- **in-flight 去重**（`inflight` Map）：同一个 cache key 并发请求共享一个 Promise
- **图尺寸 1024×1024**：替代 1024×1536 竖图，省 30-40% 出图时间
- **并发闸**（`imageGen.ts`）：`IMAGE_CONCURRENCY` 限制同时活跃的图生成调用数
**为什么好**：单节点从 ~120s 压缩到用户体验可接受的区间；in-flight 去重防止 prefetch 和用户请求打架。
**可复用经验**：AI 应用的性能优化往往不在代码层面而在"调用策略"层面——少调、并行调、预热调。

## 需要改进的地方 ⚠️

### 1. 前端主线三次切换浪费了 6-8 小时
**具体问题**：前端主线在 24 小时内从 React 19 切到 guofeng.html 再切到 kacha.html，每次切换虽然利用了共享模块，但仍需重写 UI 适配层、重新对接 API 调用、重测所有交互路径。
**根本原因**：早期（ADR-002）的框架选型（Vue 3 → React 19 的偏差）没有建立统一的原型评选标准。如果一开始就做 3 个风格的 HTML 原型 + 让团队/评委投票定稿，可以节省一个下午。
**改进方案**：黑客松的前端选型应使用"风险最低的交付路径"而非"最熟悉/最现代化的框架"。原生 HTML 在 25h 内不输 React/Vue，尤其当视觉一致性是评审维度时。

### 2. 队友需求文档的"凌晨突袭"
**具体问题**：5.23 凌晨队友提交了一份全新需求文档，方向与已有 MVP 存在较大偏离（品牌名、文风、社交功能、OCR 入口等），触发了 ADR-004 和 ADR-005 两个决策回合，消耗了队长凌晨的决策精力。
**根本原因**：赛前团队没有做需求对齐。队友在赛前按自己的理解写了完整需求文档，但仓库已基于不同方向推进到 T13 后端 + 前端 MVP 接入。
**改进方案**：下次黑客松在 5.23 10:00-11:00 赛题发布后，先用 30 分钟做全员需求对齐，把"必须做 / 可以做 / 不做"清单口头对齐后再启动开发。任何方向变更由队长书面确认（用 ADR 或 Git checkpoint 记）再进入开发。

### 3. VLM 模型选型的摇摆与试错
**具体问题**：ADR-002 选豆包 vision-pro（字节生态 + 中文调性），实际开发中因为中转网关的便利性直接切到了 gemini-2.5-flash-nothinking，兜底从 GPT-4o 切到 gpt-4.1-mini。豆包 vision-pro 从未真正被用在生产路径。
**根本原因**：中转网关（OpenAI-Next）提供了"一套协议接所有模型"的便利，团队倾向于优先试延迟最低/价格最低的模型，而非按 ADR 的评审导向选择。
**改进方案**：技术栈 ADR 应标注"验证状态"——哪些选型是理论选型、哪些已完成 smoke-test 验证。选型基准应包含一次 5-10 条样本的 prompt 验收，结果附在 ADR 里。

### 4. README 和 retrospective 未及时更新
**具体问题**：README.md 在 MVP v2.1 阶段（5.23 凌晨）更新后就停更了，实际的 Part 2 v2 重做（40 节点树）、kacha.html 主线切换、ADR-007/008 都没有反映到 README 中。retrospective.md 保持空白模板。team.md 也只填了队长一人。
**根本原因**：AGENTS.md 的"文档更新模式"定义了 AI 应主动更新文档，但最后 12 小时进入了高强度开发模式，更新文档的优先级被让给了编码。
**改进方案**：下次设置"文档硬性截止时间"——如 5.24 10:00 文档冻结，AI 在这之前必须将所有关键决策和状态同步到 README 和 retrospective。

### 5. Part 2 图像生成延迟未降到 demo 友好区间
**具体问题**：即使做了推测预热 + 缓存，冷启动节点仍需 ~120s（gpt-image-2 是主瓶颈）。演示时需 `npm run warmup-story` 提前灌满才能秒回，但这样一来"实时生成"的 AI 展示效果就变成了"播放缓存"。
**根本原因**：gpt-image-2 本身延迟高，且图像生成从 gpt-image-2 → gpt-image-1 → dall-e-3 的降级链在延迟上差异不大。缓存预热绕过了延迟问题但没有解决它。
**改进方案**：如果续作这个方向，应探索本地小模型（如 SDXL-Turbo / FLUX）做实时图生成，或改用纯文本剧情+前端合成配图的混合方案，把图生成的延迟从用户路径中移除。

## 技术总结

### 技术亮点

1. **VLM 调度引擎**（`server/lib/vlm.ts`）
   - 实现方式：双模型 × 2 次 retry 阶梯调度，每个步骤记录 trace
   - 创新之处：`postProcess` 用后端强制覆盖保证 score→tier→sign_type 三元组一致，防止 VLM 幻觉
   - 可复用性：直接抽取为通用 VLM 调度库

2. **自研 sticker-engine**（`_shared/sticker-engine.js`）
   - 实现方式：纯 DOM 拖拽/旋转/缩放/撤销引擎，327 行无依赖
   - 创新之处：handle 驱动的旋转+缩放合一，undo 快照自动裁剪到 20 步
   - 可复用性：任何需要轻量贴纸编辑器的场景都可直接复制

3. **统一磁盘缓存**（`server/lib/cache.ts`）
   - 实现方式：命名空间/哈希/版本号三级寻址，tmp+rename 原子写
   - 创新之处：`getOrSetJson` 模式一站式实现"查缓存→生成→写回"，`CACHE_VERSION` 批量失效
   - 可复用性：标准 AI 应用缓存模式

4. **推测预热 + in-flight 去重**
   - 实现方式：节点 N 生成后 fire-and-forget 触发子节点，同 key 并发请求共享 Promise
   - 创新之处：预热不阻塞主请求，去重防止预热和用户请求打架
   - 可复用性：树形 API 调用的通用优化模式

5. **前端 8 屏单文件架构**
   - 实现方式：1524 行 HTML + CSS + JS，所有屏幕在同一 phone shell 容器内通过 CSS opacity 切换
   - 创新之处：零构建、零路由、零框架依赖；8 个独立 screen div + 统一的 `go()` 状态管理
   - 可复用性：黑客松演示产品的最佳前端架构

### 技术债务

1. **Part 2 v2 第一版代码未清理**
   - 问题描述：`src/frontend/` 下的 React Part 2 v2 实现（StoryV2Screen、CameraShutter 等）在 kacha.html 定稿后已不再是主线，但仍保留为可跑状态
   - 产生原因：进度压力下"保留不删"是最快选择
   - 如果有时间应该：整理 `src/frontend/` 为纯示例子项目，或在 README 明确标注"非主线、可跑、无维护"

2. **imgCompress.ts 未集成到主流程**
   - 问题描述：`server/lib/imageCompress.ts` 存在但仅在 story 节点的 reference image 处理中使用，Part 1 的前端压缩没有后移
   - 产生原因：前端上传统一压缩，后端未做 fallback 压缩

3. **硬编码的 CORS 策略**
   - 问题描述：`local-server.ts` 中 CORS 全开（`Access-Control-Allow-Origin: *`），适合开发环境但不适合生产
   - 产生原因：本地服务器仅用于演示，安全性不是约束

### 踩过的坑

| 问题 | 耗时 | 解决方案 | 如何避免 |
|------|------|----------|----------|
| gpt-image-2 偶尔不复制人脸 | 2h | ADR-007 列为已知风险，加强 prompt | 图像生成不依赖 face-swap 做核心功能 |
| 单节点冷启动 ~120s | 1h | 缓存预热 + 推测预热 + in-flight 去重三管齐下 | 在选定图像生成模型后先测延迟基线再写 prefetch |
| 前端 3 次切换 | 6-8h | 共享 `_shared/*` JS 模块复用 | 先做原生 HTML 视觉原型投票再定框架 |
| 并发预热时网关 connection reset | 1h | `imageGen.ts` 加并发闸 + fetch failed 重试 | AI 网关在高并发下需要限流 |
| demo 照片哈希匹配不中 | 0.5h | `shortHash` 截 16 位 + `demo-match.ts` 双通道 | 测试环境的数据生成和验证要写 smoke test |

## 三个最重要的经验

1. **黑客松的产品演化不是线性推进，而是不断"刹车-转向-加速"的循环。** ADR 体系是让每次转向都有记录、有理由、可追溯的关键基础设施。没有它，6 次产品迭代 + 3 次前端切换会彻底混乱。

2. **演示连贯性 > 技术炫技。** 最后 6 小时切换到 kacha.html 单文件架构是整个项目最关键的决定。8 屏在同一个手机壳内无缝切换，比任何"我们用了 React 19 + Konva + TailwindCSS"的技术堆叠更能打动用户和评委。

3. **兜底不是备选，是主干。** demo hash 匹配、`?mock=1`、持久化缓存、预热脚本——这些"非 AI"的东西最终决定了演示能否跑通。AI 实时调用永远有不确定性，黑客松演示应该默认走最稳路径，AI 作为"展示彩蛋"。
